## 目标

检验「会自己查数据的 agent」能不能替代一部分治理，以及有了指标层之后它还有没有用：在 L0、L1、L2 上给模型一个只读的查询工具，看它能把多少差距补回来、要多付多少 token 和时间。

## 规格

- 与对应直答单元相同的系统提示和语义上下文，另加一个工具 `run_sql(query)`：只读（拒绝任何写操作和 DDL），每次最多返回 50 行，30 秒超时。
- 由模型决定查不查、查什么、何时交卷；最多 8 步工具调用，之后必须给出最终查询；最终查询按直答的规则执行和修正一次。
- 单元与工具后端：SQL-L0-E 和 SQL-L1-E 的 `run_sql` 走 `chdb_retail`；SQL-L2-E 的 `run_sql` 和最终查询都走 `cube_sql`（T16）。
- 系统提示里只增加一段工具说明，不增加任何关于数据的提示。这段说明在开跑前写好，打 tag `harness-agent-v1` 冻结，并原文列进报告。
- 中文题集全部，每题 3 次。

## 来自 T11 的交接（2026-10-16）

**一、回显给 agent 的行数要有上限，而且各档位必须一致。** 直答单元里模型看不到数据行；**探查 agent 不同，它会看到 `run_sql` 的结果**。而参考结果最大有 **561,293 行**，塞不进 prompt。所以要设一个**回显行数上限**（截断并明确告诉模型「结果已截断，共 N 行」，不要假装完整）。

这个上限是**档位之外的变量**：L0-E / L1-E / L2-E 必须用同一个值，否则比较的就不只是语义层。值写进卡片记录，不得逐题调整。

注意与执行器的 `max_result_rows`（200 万，超限直接报错）区分开：那是**执行**的上限，这是**回显**的上限，两回事。

**二、本卡是全项目成本最高的地方。** 直答每题 1–2 次调用；探查 agent 最多 8 步，**每一步都要重发不断变长的对话**，而变长的后缀是缓存未命中的。T11 实测冷热成本差 20–30 倍，所以这里的费用模型和直答完全不同。开跑前用 `--dry-run` 按**实际步数分布**估，不要按「题数 × 8」上限估，也不要套用 T13 的每题成本。

**三、超时与资源闸同直答**（120 秒 / 2,000,000 行 / 16 GiB，`throw` 不截断），库范围限制同样生效——agent 的每一次 `run_sql` 都要过同一道检查。

## 交付物

- `runs/<run-id>/` 下三个单元的 JSONL，每条另记步数、每步的工具调用、总 token、总耗时。
- `reports/results/explorer.md`：三个单元的准确率与四种结果占比，与直答 L0、L1、L2 对比；按题目的「语义依赖」（可从数据发现 / 只能由业务告知）分开列；每题平均步数、token 与耗时（agent 税）。

## 验收

- 记录数 = 题数 × 3 × 3，无缺失。
- 工具调用全部是只读的（日志核对）。

**固定参数（三个单元同一个值，不得逐题或逐单元调整）**

| 参数 | 值 | 说明 |
|---|---|---|
| 回显行数上限 `ECHO_ROWS` | **50** | 超出时只回显前 50 行，第一行写明「结果已截断，共 N 行，以下只显示前 50 行。」 |
| 单次回显字符上限 `ECHO_MAX_CHARS` | 20,000 | 防止单个超长值（如 `groupArray`）撑爆上下文；截断时注明。不是行数上限的替代 |
| `run_sql` 次数上限 `MAX_TOOL_CALLS` | 8 | 格式错误、未知工具的调用也计数；同一回复里超出上限的调用不执行，回「已达上限」；用完后下一次请求带 `tool_choice: "none"`，模型只能交卷 |
| 执行超时 | `run_sql` **30 秒**（规格）；最终查询 120 秒（同直答） | 用户 2026-10-19 裁决，见偏离第 1 条 |
| 资源闸 | 200 万行 / 16 GiB，`throw` 不截断 | 同直答；回显上限与执行上限是两回事 |
| 库范围、只读检查 | 同直答（`ChdbExecutor`：单条 SELECT、禁止改会话设置、按单元的库范围、表函数白名单） | 每一次 `run_sql` 都过同一道检查 |

**实现**

- `harness/agent_prompt.py`：工具说明 `TOOL_SECTION`、`run_sql` 的函数定义、截断与报错的回显写法。**整个文件是 `harness-agent-v1` 的冻结范围**。系统消息 = 对应直答单元的系统消息（逐字节）+ 工具说明。
- `harness/run_agent.py`：运行器。最终答案（不带工具调用的回复）照直答规则解析、执行、报错修一次（修正请求带 `tool_choice: "none"`）；打分照 PR #100 放子进程、10 秒超时记 `pending/score_timeout`。思考模式下 API 要求工具对话里每条 assistant 消息带回 `reasoning_content`（否则 400），全部带回。
- 版本闸：题库不是 `--eval-tag`、语义层不是 `--semantic-tag`、`harness/prompt.py` 不是 `harness-v1` 的、`harness/agent_prompt.py` 不是 `harness-agent-v1` 的，都拒绝开跑（dry run 对最后一条只警告）。任何一次调用的指纹不是 G3 的就停。
- 日志：直答的全部字段，另加 `steps`（每次带工具调用的模型调用：每个工具调用的查询、执行摘要、回显行数、是否截断、原始结果哈希）、`n_tool_calls`、`n_steps`、`hit_tool_limit`、`tool_time_s`、`wall_s`、`agent`（上限与工具说明哈希）。`turns` 只放最终答案与修正，`harness.rescore` 不用改即可离线重评。runs-raw 另存每次工具执行的完整结果 `<qid>_r<rep>_t<call>_c<k>.exec.json`。
- `harness.run_agent.summarize`：直答汇总 + 步数分布、工具调用状态、只读核对（`tool_forbidden_statements`）、每题平均 token / 耗时 / 费用。
