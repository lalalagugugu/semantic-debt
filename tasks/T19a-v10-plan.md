## 六、本体补测的假设（草案，用户定稿前 T34 不开工）

用户 2026-11-03 指出：前几轮有些单元没想清楚就跑，后面补数据、分母在 98 和 109 之间变。每个新单元开跑前先写清：假设、从哪来、预测、什么结果改变哪句结论、能测出多大的差。

**这个问题从哪来。** 业界「本体 / 知识图谱让大模型问数更准」的说法，常引的是 data.world 的基准（Sequeda 等，2023）：同一批题，直接写 SQL 约 16%，在知识图谱上写 SPARQL 约 54%（数字凭记忆，引用前核对原文）。那次对比同时换了三样：业务内容（本体里有业务定义，SQL 那边只有表结构）、内容的写法、查询语言加映射引擎。本实验已经单独测了内容（L0 / R 到 L1 到 L1+）。剩下两样要拆开测。

**A. 写法（L3a-full）：内容不变，全部写成本体，模型仍写 SQL。**
- 支持「有帮助」的理由：本体把关系、类的归属、约束写成显式结构，可能减少「是什么 / 属于谁」一类的错（L1 的 44 次错里有 22 次）。
- 支持「没帮助或更差」的理由：L1 已经是结构化 YAML，关系、枚举都写了；本体要模型把概念再映射回表和字段；token 约 5 倍。旧 L3a（只换 109 条）和 L1+ 没有差别（93.2 对 92.9）。
- 预测：没有大的差别；如果有，更可能是变差。
- **天花板问题**：L1+ 已到 93%，错的空间约 7 个百分点；98 题的同题配对区间约 ±5 个百分点。在 L1+ 上比，测不出「有帮助」。要测「有帮助」，得在还有错的地方比：L1 文字对 L1 本体（L1 是 85%）。
- 能测出多大的差：约 5–6 个百分点以上。所以这组实验能回答「有没有大的作用」（比如业界说的那种量级），回答不了几个百分点的小作用。报告要照这个写。

**B. 查询（L3b）：模型写本体查询（SPARQL），引擎按映射编译成 SQL。**
- 和指标层是同一类做法：口径和关联路径由人维护的映射执行，不由模型现写。本实验里指标层的结果是：只能调指标时覆盖不足（JSON-L2 41.8%），覆盖的题上也没有更准（87.4 对 91.9）。
- L3b 和指标层的区别：SPARQL 能自由组合概念和关系，不像 JSON-L2 只能调现成指标。所以要测的假设是「能不能拿到指标层那种由引擎保证的口径，又不丢覆盖」。
- 预测：覆盖高于 JSON-L2，但到不了 100%（窗口函数、时间计算、ClickHouse 函数可能写不了）；覆盖的题上不比 L1+ 写 SQL 更准，因为 L1+ 的错主要是「怎么算」，映射照样要人写对；模型对 SPARQL 不如对 SQL 熟。
- 先做可行性（不花模型钱）：能覆盖多少题、映射要多少人工。覆盖太低就不值得跑模型。

**分母（事先定）**：主结果只报 98 题；测试集 49 题只在和调优单元比时用；不报 109 题。

**比较层级（用户 2026-11-03 澄清，取代此前的说法）**：每组比较只换写法，内容逐条相同；任何单元都不同时改内容和写法。旧 L3a（L1 原文是文字、109 条是本体）是混合写法，两个问题都答不干净，所以不复用。

| 组 | 文字 | 本体 | 内容 | 回答的问题 |
|---|---|---|---|---|
| 1 | SQL-L1 | SQL-L1-onto | L1 全部 | 语义写得好（完整，但有歧义）时，本体写法有没有帮助 |
| 2 | SQL-L1plus | SQL-L3a-full | L1 全部 + 109 条 | 语义已经写得很详尽（逐条消歧）时，还值不值得换成本体 |

两组能测出的方向不同：第 1 组 L1 是 85%，有空间看出「有帮助」；第 2 组 L1+ 已到 93%，主要能看出「会不会变差」，看不出小的帮助。两组的差别（本体在 L1 上的作用减去在 L1+ 上的作用）不单独下结论，没有足够的题数。4 个单元，粗估 25 元以内；新跑的两个文字单元兼作指纹对照。

## 七、本体结论的口径（用户与协调会话 2026-11-04 讨论）

- **测的是什么**：W3C 标准写法（OWL 2 / SHACL Core），内容逐条相同、只换写法，模型仍写 SQL（L3a-full、L1-onto）。不是 Palantir 那类「业务对象 + 挂在对象上的函数和动作 + 权限」的对象模型；也不是 L3b（模型写本体查询，引擎按映射编译成 SQL）。报告第 4 节开头先定义「本体」指哪一种。
- **能说的**（结果出来后按实际数字改）：只把语义层换成本体写法，准确率有没有提升；不能说「本体没有用」，也不能泛化成「本体不比文本更深」。
- **已经有的发现，和结果无关**：标准本体语法能形式化的基本是「是什么 / 属于谁」（类、划分、键、取值条件）；「怎么算」（聚合、除法、默认值、窗口）没有标准写法，L1 的 69 个指标和 15 条约定全在第 2 档。L1 的错里「怎么算」占 19/44，这部分换写法帮不上。
- **「带函数」的那一类**：口径做成可执行定义，本实验里对应指标层（SQL-L2、JSON-L2），L3b 的映射也属于这一类。已有结果：可执行口径在覆盖的题上没有比写好的文字更准，只能调指标时覆盖不足。Palantir 式的对象模型 + 函数 + agent 调工具，最近的是指标层加探查 agent，本实验没有完整测。
- **给读者的可行动结论（草案）**：已经有写好的文字语义层，把它转成本体格式喂给模型，不是提高准确率的主要投入方向；钱应该花在口径写全、消歧（L1 → L1+）。本体的价值如果有，更可能在跨系统整合、治理、给 agent 当可调用的对象模型，这些本实验没测。
