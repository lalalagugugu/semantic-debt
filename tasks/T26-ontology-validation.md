# T26 L3a 本体质量校验（免费）

- 状态：未开始
- 负责：Claude Code（新会话，普通模式；不得由协调会话或其子 agent 代做）
- 模式：open
- 依据：用户 2026-10-25「L3A 里头写的本体，既没有跑过推理机，也没有跑过 SHACL 约束检验，怎么判断我们写的本体是高质量的呢？……所以本体校验还是要做的。」
- 预算：0（不调用付费模型）
- 为什么归 Claude Code：L3a 的 Turtle 生成器和逐条对应核对器（`render/l1plus.py`）都出自 Codex 的 T22b，核对器只解析生成器自己用的 Turtle 子集。独立校验按 AGENTS.md「分工」第 1 条跨厂商。

## 要回答的问题

1. L3a 的本体本身质量如何：标准工具能不能读、逻辑上自不自洽、建模有没有明显错误？
2. L3a 没有比 L1+ 再往上涨，有没有可能是本体写得不够好，使得**本来能拿到的提升没有拿到**（不是「本体差导致变差」）？「不够好」分两种：写错（公理含义与原文不符、逻辑矛盾）和写得浅（109 条里只有 30 条形式化）。本卡能回答前一种；后一种要换更深的形式化重跑才能回答，本卡只报告哪些条目可以进一步形式化、对应多少道 L3a 答错的题，作为下一期 L3b 的输入。
3. 本体能不能校验语义层和数据：如果把修正前的层级和真实数据放进去，标准约束校验能不能查出已知问题？

## 步骤

1. **语法**：用标准 RDF 解析器（rdflib）解析 L3a 的全部 Turtle（`uv run python -m render.l1plus` 的产物），报三元组数、命名空间、解析错误。
2. **逻辑一致性**：用 OWL 推理（owlrl 的 OWL-RL 闭包；能装上 HermiT / Pellet 类 DL 推理器就再跑一遍）。报：是否不一致、不可满足的类、子类关系环、推理新得出的类成员是否与 L1+ 文字矛盾。
3. **建模检查**：逐条核对 30 条形式化条目（17 组别名、13 组层级）的公理方向与含义是否和 `semantic/l1plus.yaml` 原文一致（例如子类方向、别名是等价还是标签、层级用的是哪个属性），以及常见建模缺陷（属性缺定义域 / 值域、同一实例重复声明、标签与注解混用）。每条给「一致 / 不一致 / 拿不准」并写理由。
4. **SHACL 自检**：用 pySHACL 对 L3a 自带的 shape 跑一遍，确认 shape 本身合法、能执行。
5. **数据回测**（本步说明本体「能不能」查出问题，不说明它「会不会」主动发现，报告里照此措辞）：
   - 从 Parquet 取科目表、员工表、产品表的必要列，转成实例数据，规模可抽样但要写明抽样方式；
   - 使用**修正前**的层级关系（即原始数据里的父子列，不是 L1+ 断环后的版本），另写最少量的 shape：层级无环（SHACL-SPARQL）、外键可解析（孤儿行）、取值大小写一致；
   - 报：能否查出科目树和员工汇报链的成环、FactOnlineSales 的孤儿 ProductKey、Blue / blue，以及查出了什么之前不知道的问题。另写的 shape 单列，不改 L3a。
6. **「本体不够好、错过了提升」的检验**（只用现有日志）：
   - 写错：按步骤 2、3 的结论，把有问题的条目对应到它涉及的题，看这些题上 L3a 是否答错。若没有问题条目，写明这一点。
   - 写得浅：列出 79 条注解保留条目里哪些在 OWL / SHACL 里有现成写法可以形式化（例如固定取值、互斥、基数、层级），以及这些条目涉及的题里 L3a 答错多少。只做清单和计数，不改本体。
7. 报告 `reports/validation/l3a-ontology-validation.md`：每步一节，给可复现命令；只写条目编号和题号，不写题面。

## 事先登记（在看到结果前写定；用户 2026-10-25 同意）
