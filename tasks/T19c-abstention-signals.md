## 目标

L1 档错答 35%、拒答 0%：模型答错时从不说「没把握」。人考试时知道「这题我肯定会」和「这题硬着头皮答」。本卡检验模型的自我判断和对错是否相符，决定第二期是否做「按把握分流」（有把握的直接给，没底的标注核对）。

## 第一部分：现有日志里的隐含信号（不调用模型）

- 信号：思考 token 数（`usage.reasoning_tokens`，首轮）；首轮是否执行报错。
- 范围：SQL-L1 全部非 judge 作答（327 次），主表与低区分度分开。
- 指标：每个信号区分对错的 AUC；按信号分档的正确率。

## 第二部分：自评把握（不重跑作答）

- 对 SQL-L1 的 327 次作答，各在原对话之后追加一轮：原系统消息、原问题、原作答（不含思考内容，不含执行结果）之后，发一条固定的追问：请在不看执行结果的情况下，自评这条查询答对题目的把握，三选一：A 肯定对，B 大概对，C 没底；并用一句话说明原因。输出固定 JSON。
- 原作答与判定不变；追问的提示词在第一次付费调用后不再改，sha256 记入日志；指纹不符即停；JSON 解析失败如实记为 `unparsed`，不重试。
- 系统消息须与 T13 运行时逐字节相同（按日志里的 `system_sha256` 核对，不符就停）。
- 日志 `runs/<run-id>/`（只含题号、次数、档位），原始响应放 `$SEMDEBT_DATA_DIR/runs-raw/<run-id>/`，`runs/INDEX.md` 记一行。

## 判定规则（开跑前冻结，不得看完数据再改）

- **证实（模型知道自己会不会）**：A 档正确率 ≥ 90%，且 A 档占作答 ≥ 40%，且 C 档正确率 ≤ 50% → 第二期候选「按自评把握分流」单元；中期报告写「可以只直接给出有把握的答案」。
- **证伪（模型不知道自己会不会）**：三档正确率两两相差都 < 10 个百分点，或 ≥ 80% 的作答自评为 A → 自评把握不可用；中期报告写「模型答错时也自认为有把握」，改进只能靠外部校验或语义层。
- 介于两者之间：如实报告，不建议新单元。
- 第一部分的信号只作参照：AUC ≥ 0.70 记为「有用的隐含信号」，不单独触发新单元。

## 口径细化（2026-10-23 执行会话补，写于计算任何信号与对错的对照之前；只细化卡里没写的操作口径，不改上面的判定规则）

1. **范围**：源运行 `20261018-T13-sql-direct-01-rescore-01` 的 SQL-L1，`scoring` 不是 judge 的 109 题 × 3 次 = 327 次。「对」= `final.outcome == correct`；错答、执行失败、拒答都算「不对」。主表 = 98 题 294 次，低区分度 = 11 题 33 次。
2. **第二部分判定只在主表（294 次）上下**，低区分度与合计只列数、不判定（与 `sql_direct.md` 主表口径一致）。
3. **第一部分的方向先定**：思考 token 越多、首轮执行报错，视为越可能「不对」；AUC 按这个方向算（`不对` 为正类，并列记 0.5），低于 0.5 照实报告、不翻转。「首轮执行报错」= 第 0 轮 `exec.status == error`。思考 token 的分档 = 主表 294 次的四分位点，低区分度用同一组切点。
4. **追问的对话**：系统消息（逐字节同 T13）、原问题、**被评分的那一轮**的作答原文（`turns[-1]` 的 `content`，不含思考）、固定追问。首轮报错后修正过的作答（`fixed`），中间的报错消息与第一次作答都不放，因为报错就是执行结果。
5. **`unparsed`** 不进 A/B/C 任何一档，单独计数；「≥ 80% 自评为 A」与各档占比的分母是解析成功的条数。某一档 0 条时，它不参与「两两相差」的比较；C 档 0 条则「C 档正确率 ≤ 50%」不成立（不能证实）。
6. **证实与证伪同时成立**（例如 ≥ 80% 自评为 A、而 A 档 ≥ 90% 对、C 档 ≤ 50% 对）：记为「矛盾」，按「介于两者之间」处理——如实报告，不建议新单元。（第一部分已算出后、第二部分付费调用之前补写。）
