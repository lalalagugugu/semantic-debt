## 目标

写一个确定性的结果比对器，并用外部基准公开的 600 条候选 SQL 验证它的判定是否合理。

## 比对规则（来自设计 v5，不得自行改动）

1. 执行候选查询，与参考结果比对完整结果集（不截断）。
2. 数值相对误差 0.5% 以内算相等；字符串去首尾空格后比较。
3. 不看列名和列顺序；候选多出的列不扣分；参考的每一列都要在候选里找到取值一致的一列。
4. 只有问句要求排序或「前 N 名」时才比较行序；「前 N 名」在第 N 名有并列时，并列者任一都算对。
5. 小数与百分数等价（0.9967 与 99.67）。
6. 一道题可以有多份参考结果（「可接受解读」），与任一份一致就算对。
7. 输出四种结果之一：`correct`、`wrong`、`exec_error`、`refused`（候选输出 `CANNOT_ANSWER`）。准确率只把 `correct` 记为 1。

## 交付物

1. `harness/scorer.py` 及单元测试（覆盖上面每条规则，至少各两个用例）。接口：`score(candidate_rows, refs, rules) -> outcome`，不依赖具体执行器。
2. `reports/validation/scorer_check.md`：对 600 条候选（6 个系统 × 100 题）在我们的数据上重新执行并打分，与对方公布的严格判定、宽松判定逐条对比，列出所有不一致并归类：我们更宽（如并列、百分数）、我们更严、我们的 bug（必须修掉）。报告里只写题号和归类，不写题目原文。
3. 执行候选 SQL 用 `$SEMDEBT_DATA_DIR/chdb-eval`（不要打开 `$SEMDEBT_DATA_DIR/chdb`，那份给 Claude Code 用）。

## 验收

2026-10-14 用户裁决换掉了原来的「一致率 ≥ 95%」，依据和理由见 `decisions/2026-10-14-scorer-contract-and-acceptance.md` 第二节。简述：冻结规则故意在四处比外部 strict judge 更严，约 10% 的差异由规则本身产生，追 95% 只能放宽冻结规则；而项目自己的 G0 口径（`START-HERE.md` 第 8 节）本来就是「不一致的地方都有解释」。

- 单元测试全过。
- 600 条逐条有判定与归类；每条与外部 strict judge 不一致的，都归到**具名原因**（冻结规则的具体条号，或缺陷）。**「原因不明」为 0。**
- **评分器与契约缺陷为 0**，不能靠解释过关。当前已知必须修掉的三条（来自独立复核）：
  1. 行序判据不得取参考结果的物理行序；参考 SQL 无最终 `ORDER BY` 时 `ordered` 为 `false`。
  2. 边界并列组必须确定性可复现（S-R Q88 出现过 24 行 vs 26 行）。
  3. 「舍入差异都小于 1%」的表述不成立，报告须改为实测值（最大约 17.13%）。
- 应用独立复核认定的 **8 条改类**，并给出修正后的互斥主分类计数（合计仍为 68）。复合原因要有明确的主分类选择顺序和次级标签。
- 每类「我们更严」单独列条数，并写明它会怎样系统性影响全部单元的准确率——这是 G0 要用户看的东西。
- 判错的 case 打敏感性标记：区分「数值列全对、仅字符串/标签列不符」与「数值本身不符」，供 T19 报「严格口径 X% / 放宽字符串格式后 Y%」。**只是报告层的数字，不改判定。**
- 86.7%（515/594）与 88.3%（515/583）两个数字照写进报告，不因换口径而隐去。
- **不再要求任何数字阈值。**
