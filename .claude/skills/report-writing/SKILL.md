# 报告写作规则（来自 v6–v10 的用户批注）

读者设定：正在考虑或已经在做相关项目的业务和数据负责人。懂业务、懂行业通用词，不懂本实验的内部名字。

## 一、全文规则（每条都要逐句全文执行，不只改被批注的地方）

1. **正文不放句中限定。** 限定、免责、方法细节不插在句子后面。真影响读者判断的，进「局限」，每条一句；不影响的删掉。值得验证的，跑个对照再写。冷读说「说过头」，改主句本身，不是加尾巴。
2. **标题和加粗首句写结论。** 写可推广的结论，不写话题、问题或「可以参考的方法」这类空概括。先给通用结论，再给本实验的例子。标题和段首第一句不重复。
3. **每个事实交代对读者意味着什么。** 写一个事实前先问：对一个正在做这类项目的企业，这意味着什么？答不上来就删，或者改写成能推广的说法（例：不写「公开文档有错」，写「现有文档不能当金标准，要对着数据核」）。
4. **说人话。** 不用内部代号（任务卡号、run 名、单元缩写不解释就用）。行业通用词（token、系统提示词、agent）不解释；本实验自己起的名字要解释一次。英文术语给中文。「所以」前后必须真有推理关系。
5. **论断旁边要有证据，证据放在论断旁边。** 没有证据的观点标「本报告认为」或删掉。
6. **局限只放真正的局限。** 和真实项目做法一样的（例：判定规则看过错例后补、口径以业务方认可的答案为准），写进方法说明，不算局限。
7. **范围和指代只在不写会读错的地方说一次**，放表头或节首句，不要变成连篇累牍。
8. **差值的方向用文字说**（「比 L1 低 7.9 个百分点」），不让读者自己判断谁减谁。
9. **某个单元的现象，先查是不是所有单元都这样**，都这样就不写成这个单元的发现。
10. **结论范围不超过证据**：只有两组数据就不写「越……越」；区间含 0 就不写「有提升」；没测的不写成测过（例：「不依赖顾问」没测，就删）。

## 二、版式（公众号、企业微信）

- 宽表保留为表格，作者自己截图；长文字表改成「加粗首句 + 段落」。
- 代码块不手工折行（公众号可横向拖动）。
- 表不编号，正文写「下表」。
- 字数统一口径：正文 + 表格，汉字算 1，一串英文或数字算 1，标点不算，代码块不计。

## 三、流程

1. 先冻结数字，再写文字；先批一页大纲（每节一句结论）。
2. 每轮改动开新 tab，版本号递增，不在旧 tab 上改。作者的删除线 = 删除，新版连字带标记删掉；作者的直接修改全部保留。
3. 写完：冷读（没参与写作的新会话）→ 另一家核数字（T20）→ 实验描述回到任务卡和提交记录核对。
4. 冷读意见先分流：改主句 / 进局限 / 跑对照 / 驳回。动作者定过的内容前先查决定记录，冲突的问作者。不把「说过头」转成句中限定。
5. 作者批注后：把批注归纳成全文规则，交逐条清单（位置、原文、改法、对应哪条规则或哪条批注），不只改被标的地方。
6. 新数字和新说法都进出处清单，交另一家复核后才定稿。

## 四、反例（作者批注原话，供自查）

- 「说了多少次了，你可以对声明做 qualification，但不要 abrupt 以至于打断 reading flow，要么放最后局限里声明，要么你就快速跑一个对照测试」
- 「谁要读一个每句话之后都跟着 qualifier 或者免责声明的文章？」
- 「opening remark 得是 takeaway，不是问题」「直接写 conclusion 或者 actionable insight」
- 「give something more generalizable, then the concrete example」
- 「既然和真实项目一样，那为什么是本篇的局限？」
- 「如果不懂什么是 token、系统提示词，那肯定就不是本文的受众了」
