# 智能问数实测·下：Agent、本体、指标层，能替代语义层吗？

2026-11-09 · Yu HUANG

## 要点速览

换技术也绕不过写语义这件事，上线还要配外部护栏。

- **会查库的 agent 替代不了语义层。** 同样的语义说明，加上会查库的 agent，差异不显著。语义说明越差，大模型查得越多，但业务约定不在数据库里，查得再多也补不上。
- **把整个语义层换成标准本体写法，没有测到****提升。** 内容逐条相同、只换成 OWL 2 / SHACL Core 写法，大模型仍写 SQL：在 L1 和 L1+ 上，本体写法分别高 0.3 和 2.0 个百分点，差异都不显著。标准本体能写成结构的基本是「是什么、属于谁」，「怎么算」没有标准写法。
- **只能调指标或只给汇总表时覆盖不足，能答的部分也没有更准。** 用户问的一旦超出已加工的范围，要么答不了，要么答错。
- **写 SQL 不是瓶颈。** 教给大模型具体 SQL 方言的写法、给代码示例，准确率差异不显著；给了 Python，它一次都没用。因此项目的精力和预算应该放在语义上，而不是 SQL 写法。
- **大模型对自己哪题会答错分辨得不够可靠，上线要配外部护栏。** 在 L1+ 上，只在三次作答的内容一致时放行答案，作答部分的准确率从 93.9% 到 96.6%；在 L1 上，只在大模型自评的答对概率不低于 90% 时才作答，准确率从 82.0% 到 87.3%；都不足以放手让它「自动驾驶」，还要有分析师定期抽核，并把作答所用的口径和假设显示给用户。

## 实验过程说明

同一个大模型（DeepSeek-V4.1-Flash-1017）、同一份零售样例数据、98 道中文问题各答 3 次，每组对照只换一类东西，每种做法算一个「测试单元」。本篇共涉及 21 个测试单元：主表里的 11 个，另有模型指纹变了之后补跑的 10 个（第 2 节 4 个、第 5 节 6 个；**模型名称仍是 DeepSeek-V4.1-Flash-1017，变的只是接口返回的版本标识，即模型指纹**），都列在表里和附录。语义层是给大模型看的业务说明，口径是其中指标的算法定义。上篇的结论：语义说明从模拟交付质量低下的版本（L0）换成内容完整的版本（L1），准确率从 48.0% 到 85.0%；独立盲审、逐条消歧并补充常用概念（L1+）到 93.2%，上线后按错答复盘，在测试集上到 92.5%。

98 题对半分成调优集和测试集，调优只在调优集上做。准确率只看内容，查出来的数对就算对；附录另列的「格式一致评法」还要求按提示词的格式交付。比较两个单元时逐题比，差值的 95% 置信区间不含 0 才称统计显著，否则写「差异不显著」并给出差值。**不显著不等于没有差别。**

## 1. 会查库的 agent 替代不了语义层：L0 上平均查库 6.7 次，准确率 49.7%

很多人觉得摆在面前有两条路：花力气把语义层建好，或者让大模型自己查库摸清楚业务。为了验证这个想法，本实验把作答任务交给了一个可以查数据库的 agent，agent 在写答案之前可以自己查库，最多 8 步。结论是：**语义层绕不过去，加上 agent 也没有带来显著提升。**

| 测试单元 | 准确率 |
| --- | --- |
| L0 低质量语义层，直答 | 48.0% |
| L0 低质量语义层 + 会查库的 agent | 49.7% |
| L1 内容完整的语义层，直答 | 85.0% |
| L1 内容完整的语义层 + 会查库的 agent | 85.7% |

加上 agent，在 L0 和 L1 上差异都不显著（差值分别是 +1.7、+0.7 个百分点）。按上篇第 2 节的分法，把题目分成（1）解题要靠本公司业务知识的 78 题和（2）靠常识和数据就能解的 20 题，agent 在 L0 和 L1 上都没有带来显著提升，连靠常识和数据就能解的那 20 题也没有提升（L0 和 L1 上都是 −1.7 个百分点）。

**大模型确实查了库，语义说明越差，查得越多。** 本实验把每次查库按用途归了类：

| 测试单元 | 平均每次作答查库 | 看明细样例 | 查枚举值 | 交卷前试算答案 | 其他 |
| --- | --- | --- | --- | --- | --- |
| L0，+ agent | 6.7 次 | 34.5% | 9.4% | 51.5% | 4.6% |
| L1，+ agent | 2.4 次 | 7.2% | 6.0% | 83.2% | 3.6% |

「试算答案」指交卷前先把准备提交的查询跑一遍看结果。看数据和查枚举，L0 上占 44%，L1 上占 13%。

**本报告认为，查得再多、换一种查库策略，也补不上业务约定。** 「线上算哪些渠道」这种约定库里没有答案；本实验的工具说明由大模型自己决定怎么查，L1 上平均只查 2.4 次，远没有用完 8 次机会。

**用 agent 要多付费用，换来的提升不显著。** agent 每次作答的输入量是直答的约 3 倍（L1）到约 5 倍（L0），按实验时 DeepSeek 的缓存计价，费用是直答的 0.9–1.3 倍，缓存未命中时约 2–2.5 倍。

## 2. 把整个语义层换成本体写法，L1 和 L1+ 上都没有看出提升

本节的「本体」指 W3C 的标准写法 OWL 2 和 SHACL Core，用来描述「东西是什么、属于谁、有什么约束」，常被当作语义层的高级形态。本实验把语义层的内容逐条原样换成本体，大模型仍然自己写 SQL。

分两组比，每组只换写法，内容逐条相同：L1 换成本体（L1-onto），L1+ 换成本体（L3a-full）。四个单元在模型指纹变了之后同一批次重跑（见第 5 节），所以下表要单独看：表内单元之间可以比，绝对数字不和主表、上篇的数字直接比。

| 测试单元 | 写法 | 准确率 | 每次第一轮 token 输入 | 错因：怎么算 | 错因：是什么、属于谁 | 错因：SQL 问题 |
| --- | --- | --- | --- | --- | --- | --- |
| L1 | 文字 | 79.6% | 约 4.6 万 | 28 次 | 30 次 | 2 次 |
| L1-onto | 本体 | 79.9% | 约 6.3 万 | 27 次 | 26 次 | 6 次 |
| L1+ | 文字 | 91.5% | 约 7.5 万 | 16 次 | 3 次 | 6 次 |
| L3a-full | 本体 | 93.5% | 约 10.7 万 | 14 次 | 3 次 | 2 次 |

本体写法比文字在 L1 上高 0.3 个百分点（区间 −3.7 到 +4.8），在 L1+ 上高 2.0 个百分点（区间 −1.7 到 +5.8），差异都不显著。两组区间的上限都不到 6 个百分点，说明本实验里看不到大幅提升。本体写法的输入分别是文字的约 1.35 倍和 1.42 倍。

**标准本体能写成结构的，基本是「是什么、属于谁」。** 表成了类，字段成了带类型和所属表的属性，外键成了关系，枚举值成了个体。「怎么算」，即按订单还是按明细行、取哪个时间窗、分母是什么，在标准本体里没有现成写法：L1 的 15 条约定和 69 个指标，本体里只有指向表、字段和其他指标的链接，核心口径仍是注解里的文字或 SQL。109 条消歧补充里，核心内容用标准写法写成结构的只有 19 条，另有 21 条要靠本体自定义的谓词。以 L1 的本体版本（L1-onto）里、上篇第 1 节举过的销售额字段和指标「客单价」为例（节选，字符串有删节）：

```turtle
retail:FactOnlineSales.SalesAmount
  rdfs:domain retail:FactOnlineSales ;
  rdfs:comment "已扣折扣、未扣退货" .
metric:客单价
  :definition "销售额 ÷ 去重订单数" ;
  :numeratorMetric metric:销售额 ;
  :denominatorMetric metric:订单数 .
```

字段属于哪张表是结构，「已扣折扣、未扣退货」只能写在注解里；客单价的分子分母是链接，除法只在文字定义里。:numeratorMetric 这类谓词是本体自定义的，标准推理器不知道它代表除法。本实验的问数流程也没有接推理器或校验器，大模型把本体当文字读。

**已有本体的企业，可以用它查数据质量。** 本实验用少量约束回测，查出了科目树和员工汇报链的成环、线上销售表 14% 关联不上产品的行、Blue 和 blue 并存；它只能查出违反已写规则的数据。

**已经有文字语义层的企业，不必为了提高准确率把它转成本体。** 钱应该花在口径写全、逐条消歧（上篇第 3 节）。本报告认为，本体的价值如果有，更可能在跨系统整合、数据治理、给 agent 当可调用的对象模型，这些本实验没有测。

## 3. 只能调指标或只给汇总表时覆盖不足，能答的部分也没有更准

常见的说法是：让大模型照着文字自己写 SQL 不靠谱，把指标做成可调用的对象（指标层）、或者预先加工成汇总表，大模型只管「选」，就准了。本实验用 Cube.dev 的开源指标层产品搭了指标层（Cube 也是上篇里公开基准的发布方），指标口径和 L1 的文字是同一份。四种做法：

| 技术路线（测试单元） | 大模型怎么查 | 能覆盖 98 题里的 | 全部 98 题的准确率 |
| --- | --- | --- | --- |
| NL2SQL（L1） | 对明细表写 SQL | 全部 | 85.0% |
| NL2DSL2SQL（SQL-L2） | 对指标层写 SQL，可调现成指标，也可拿字段自己算 | 全部 | 83.7% |
| 基于汇总层的 NL2SQL（L1.5S） | 只给预先汇总好的表，写 SQL | 42 题 | 39.8% |
| NL2DSL / NL2Metrics（JSON-L2） | 只能调已建好的指标，输出 JSON 查询 | 37 题 | 41.8% |

**「只能调指标」和「只给汇总表」这两种做法，都限定了大模型能答什么。** 全部 98 题上它们是主表里最低的，主要因为覆盖不足：未得分的作答里，分别有 91.8% 和 89.3% 落在覆盖范围外。用户问的一旦超出已加工的范围，要么答不了，要么答错，只能再加工新指标、新维度。而 SQL-L2 可以拿字段自己算，覆盖全部题目。所以这两种做法**要追上明细表的覆盖面，就得不断加工。**

**能答的部分也没有更准。** 和 L1 比，三种做法的差异都不显著。在各自能覆盖的题上，L1.5S 比 L1 低 7.9 个百分点（区间 −19.0 到 +3.2），JSON-L2 比 L1 低 4.5 个百分点（区间 −12.6 到 +2.7）。JSON-L2 在覆盖范围内答错的 14 次，多数是读法和对象范围不对：「金额最大的一笔」应按单行销售算，算成了一整单；漏掉未归属的子品类和品牌，漏掉虚拟门店。这些都要靠语义说明交代清楚。

| 测试单元及覆盖范围 | 这些题在本做法的准确率 | 这些题在 L1 的准确率 |
| --- | --- | --- |
| L1.5S（42 题） | 84.9% | 92.9% |
| JSON-L2（37 题） | 87.4% | 91.9% |

**汇总表一多，「该用哪张」本身就成了新的口径问题。** 比如题目要的是电商销售，大模型用了全渠道表里「渠道 = Online」的那一行，那是门店表里的虚拟网店，和电商不是同一份数。

因此本实验认为，指标层的价值在复用、口径统一和性能。如果指标层里的指标和纸上的指标清单是同一份，只是换一种暴露方式，准确率不会自己涨。

## 4. 大模型写 SQL 不是瓶颈：给了 Python，它一次都没用

**大模型答错，多数是算法或对象选错，不是 SQL 写不出来。** L1 上答错或执行失败的 44 次，按主要错因归类，真正涉及 SQL 问题的只有 3 次：其中 2 次在修复一次后仍执行失败，1 次能执行但 SQL 机制用错。其余两类都是：「怎么算」（口径或算法读偏）19 次，「是什么、属于谁」（对象或范围不对）22 次。

**给了 Python 退路，大模型一次都没用。** 本实验试跑过一个带 Python 退路的规划 agent：24 道题（一、二、三级难度的题目各 8 道），在 L0 和 L1 上每题各答一次，共 48 次作答，大模型一次都没有调用 Python。参与计分的每一道题都能用 ClickHouse SQL 完整表达，包括队列留存、同店同比、购物篮这类多步计算。基于这 48 次作答，本报告认为，题目能用 SQL 完整表达时，大模型不会主动用 Python。

**教它怎么写、给它看示例，没有带来统计上显著的准确率提升。** ClickHouse 的 SQL 方言和常见的 MySQL 不少地方不一样，所以本实验把写法说明分四级逐步加厚：

| 写法说明 | 首轮报错率（全部 98 题） | 最终准确率（测试集 49 题） |
| --- | --- | --- |
| 1 级：基本规则 | 31.6% | 85.0% |
| 2 级：+ 使用条件与禁忌 | 2.7% | 83.0% |
| 3 级：+ 通用示例 | 1.7% | 86.4% |
| 4 级：+ 同类题的问法和完整写法 | n/a（只测测试集） | 85.7% |

- **首轮报错从 31.6% 降到 1.7%，准确率差异不显著。** 2、3、4 级比 1 级分别低 2.0、高 1.4、高 0.7 个百分点。执行报错时，大模型有一次看着报错修正的机会：1 级（即 L1）294 次作答里首轮报错 93 次，修一次后只有 2 次仍执行失败（能执行不等于答对）。教 SQL 写法主要是节约了这次修正。
- **准确率只看测试集。** 2、3 级是看着调优集的报错设计的，4 级的示例取自其中 6 道题的问法和完整写法，所以只有测试集对四个等级来说是公平的考试。

所以本报告认为，更详尽的 SQL 说明，也救不了大模型理解错问题和/或数据；提供的Python工具从未被大模型使用过，因此本实验无法判断。

## 5. 不加惩罚大模型几乎不拒答，自评答对概率高也不能放手

**智能问数最怕的是大模型错答但用户看不出来**：L1 的 42 次答错、复盘补语义的 12 次错答，全部能出结果，只是数不对。理想情况是：大模型或agent 要么答对，要么拒答。退一步，如果答出来的部分能到 95%，剩下的拒答然后转给人工，也能接受。本实验测了这件事，结论是：能筛掉一部分错答，但筛不干净。

本实验在 L0 和 L1 上各测两种提示：一种允许大模型没把握时拒答并要求披露自评的答对概率，另一种再加上计分规则（答对 +1、答错 −10、拒答 0）。这批补测的单元是在模型指纹变了之后才跑的（见本节末段），所以表内单元之间可以比（同一批次重跑了基线），准确率的绝对值不和主表其他单元比。

| 测试单元 | 全部 98 题准确率 | 拒答率 | 答了的部分准确率 |
| --- | --- | --- | --- |
| L0，基线 | 46.3% | 3.1% | 47.7% |
| L0，允许拒答 | 46.9% | 2.4% | 48.1% |
| L0，允许拒答 + 重罚答错 | 43.9% | 32.7% | 65.2% |
| L1，基线 | 79.9% | 0.0% | 79.9% |
| L1，允许拒答 | 82.0% | 0.0% | 82.0% |
| L1，允许拒答，只看自评不低于 90% 的作答 | — | — | 87.3% |
| L1，允许拒答 + 重罚答错 | 81.3% | 5.4% | 86.0% |

- **不加惩罚，大模型几乎不拒答。** 各 294 次作答，L0 拒答 7 次，L1 拒答 0 次。
- **重罚答错才会拒答。** 拒答率显著更高（L0 +30.3 个百分点，L1 +5.4 个百分点）。答了的部分准确率从 48.1% 到 65.2%、从 82.0% 到 86.0%，都没到 95%。
- **自评答对概率不低于 90% 也不能放手。** L1 允许拒答时 294 次全答了，准确率 82.0%。其中 157 次（53.4%）自评不低于 90%，这部分对 87.3%，依然没有到能放手的程度。

**三次内容一致也不保证对。** 在 L1+ 上看，这里的「一致」只看内容：问的对象、分组和指标一样就算一致。不筛选时，首次作答对 92 题（93.9%）。只有三次一致的题才算作答的话，答 89 题，对 86 题（96.6%）。这样过了 95% 线，代价是 9 题不答、费用变三倍；拦下的 9 题里 6 题本来是对的，还有 3 次错答三次都错的一模一样，拦不住。

**模型名称不变，服务端版本一变，准确率也会变。** 10 月下旬起，同一个 DeepSeek-V4.1-Flash-1017 的接口返回了新的模型指纹，推测服务端换了版本，模型名称没变。同样的配方重跑，L1 两次独立测量分别比主表低 5.1 个百分点（区间 −9.2 到 −1.4）和 5.4 个百分点（区间 −9.9 到 −1.4），都显著；L1+ 低 1.7 个百分点（区间 −5.8 到 +2.7），差异不显著。**所以上线后只要模型指纹一变，即使名称没变，也要拿固定的一组题重测一遍。**

本报告认为，在各种致力于消除歧义的语义完善动作之后，剩下的问题在于用户不能提前知道哪一题是错的。**如果每一题都要核，自助问数就失去了意义。**护栏的目标是降低核验的成本，比如可以考虑：

- **把依据摆出来。** 显示这次用了哪个口径、做了哪些假设，用户有机会看出读偏了没有。
- **分析师抽核。** 对已经答出去的结果按比例抽查，错答进入下一轮复盘。只靠点赞点踩不够：用户得明白正确的数是多少，才知道该点踩。

## 这份报告的局限

上篇的四条局限在本篇同样适用。本篇另有：

- **准确率只看结果，不看大模型声明的假设。** 少数作答结果对，但写给用户的假设和企业口径不一致，仍计为正确。上线后要把假设显示给用户，用户才有机会纠正。
- **参考答案也会错。** 本实验核对并修正了 5 道（附录）。上线后没有现成的参考答案，用户点踩时要有人算正确的数，并判断错在大模型、文档还是数据。
- **指标层和汇总表的覆盖取决于建了多少。** 本实验不看题建了 69 个指标，企业按高频问题建，覆盖率会不同。
- **语义层整份放进上下文，没有测检索。** 当语义层大到必须检索时，「写完整」之外还要检索得准。
- **98 道题只能测出较大的差别。** 以本体对照为例，按常用的检验标准，两组要差到约 5–6 个百分点以上才能稳定测出来；更小的差别，本实验测不出来。
- **每题独立作答，没有测澄清和多轮对话。** 真实产品可以反问，有歧义的问题可能部分靠反问解决。

## 本实验没有尝试回答的问题

方法、代码、语义层、题目和参考答案、评分规则、运行日志和大模型原始响应（含思考内容）都放在 GitHub 仓库 github.com/lalalagugugu/semantic-debt，另有一个静态对照页，把同一道题在各单元的作答并排放在一起。读者可以用这些材料继续探索：

- 换其他大模型，这些做法之间的相对关系还成立吗？它们对拒答要求的响应会有所不同吗？
- 语义层的七类内容，逐项拆开各自对准确率的贡献有多少？
- 数据清洗之后，文档能简化多少，准确率会变吗？
- 指标层叠加独立盲审消歧，和上线后复盘，能到多少？
- 让大模型写本体查询、由引擎按映射编译成 SQL，能覆盖多少题，准确率会不同吗？
- Palantir 式的对象模型（业务对象加上挂在对象上的函数和动作，由 agent 调工具作答），和写好的文字语义层比如何？
- 同样的语义内容放到 Power BI（DAX）上，结论还成立吗？
