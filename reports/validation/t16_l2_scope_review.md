8 个成功探针按成员名归一化列序，全部与独立查询原始事实表得到的结果一致。不能按 JSON 请求中 measures 的顺序直接比较位置：Cube 返回列序不一定等于请求顺序。

另有两个数值维度极值通用对照（产品单位成本、全渠道退货金额）验证“维度降序 + limit 1”与物理 MAX 相等，防止仅因没有 MAX 度量而误判覆盖。没有取用任何题目的查询。

可交 T12 的通用说明建议（没有改写冻结说明）：

1. 复合指标已在所属 Cube 内对齐事实来源，查询用该 Cube 的日期成员筛选；JSON 的 timeDimensions 和 SQL 的 WHERE 都遵守这一点。不要因为公式内部用到销售，就额外引用 sales 的日期。
2. 已定义所属 Cube → 公共日历连接时，可用公共日历日期；本次两个复合 Cube、同一整月范围验证成立。此结论不保证任意图路径或任意多事实 Cube 都可连接。
3. 月粒度目标与日粒度实绩的直接比较，使用同一完整月份范围。本次仅验证完整月，不声称半月筛选会把月目标按天摊分。其他时间粒度须另验。
4. SQL 中 CROSS JOIN 仍由 Cube 的已定义连接图解析，不能凭 CROSS JOIN 创建事实表间的新路径；JSON 加入另一事实表筛选也不能创建路径。

## Q50 SQL 错误归因

修正后的失败属于**引擎限制／生成 SQL 缺陷**：Cube 翻译后的 ClickHouse SQL 出现空标识符，原文含 `Syntax error: failed at position 152 (``)`。完整返回错误保存在数值核查 JSON，未脱敏。

已有对照仅替换输出别名为 ASCII 后可执行，先前审查也验证了其结果；这说明另一通用写法能绕过该缺陷，不改变本次失败由引擎生成非法 SQL 引起的事实。须区分“实际错误归因”与“整题是否存在其他可表达写法”。此前将 SQL 四条全写成说明缺口的汇总不适合作为错误层面的归因；至少 Q50 应改用本条结论，历史日志不改。

按最新 #143 的错误归因规则，同样核对 Q76、Q80、Q82：四条最终错误原文都有生成 SQL 的空标识符语法错误，故错误层面为引擎限制 **4/4=100%**，不再沿用旧报告的 0/4。说明补条件可以降低触发概率，但不能把引擎缺陷算作模型语法写错。四条错误原文一并留档。

JSON Q50 的覆盖分类仍为 d（必答增长额没有现成可见成员），与 SQL 引擎错误是两件事。该归因更新不是新实验，不触发任何模型运行。
