# L3a 本体质量校验（T26）

本报告只写条目编号和题号，不写题面、参考 SQL 或作答内容。所有步骤免费，没有调用付费模型，也没有改动 `semantic/`、`render/l1plus.py` 或 L3a 产物。被校验的 Turtle 由 `render/l1plus.py`（T22b，Codex）从 `semantic/l1plus.yaml` 生成；脚本先核对它与模型实际看到的 `build/contexts/SQL-L3a.yaml` 中的 `ontology_turtle` 逐字节相同，再开始校验。

## 复现

```sh
export UV_CACHE_DIR="$TMPDIR/uvcache"
uv run python -m render.l1plus                       # 生成 SQL-L3a 上下文（对应核对报告内容不变）
uv run --group ontology python -m scripts.t26.ontology_check syntax reason model shacl   # 步骤 1–4，约 10 秒
uv run --group ontology python -m scripts.t26.ontology_check data                        # 步骤 5，约 7 分钟（读 Parquet）
SEMDEBT_EVAL_DIR="$SEMDEBT_DATA_DIR/eval-ro-eval-v1.2" \
  uv run --group ontology python -m scripts.t26.ontology_check missed                    # 步骤 6
uv run --group ontology pytest tests/test_t26_ontology.py
```

每一步的完整结果写在 `reports/validation/l3a-ontology/<步骤>.json`，下文的数字都来自这些文件。新依赖 rdflib 7.6.0、owlrl 7.6.2、pyshacl 0.40.1 只放在 `pyproject.toml` 的 `ontology` 依赖组里，已有依赖的版本没有改动。

## 结论（三个问题）

1. **本体本身的质量。** 能用标准工具读，逻辑上自洽，30 条形式化条目里 28 条与原文一致、1 条不一致（E07）、1 条拿不准（E09）。主要问题不在「写错」，而在「写得浅」：
   - 原文有 9 个层级条目写了「互斥 / 覆盖」，本体里一条不相交公理都没有；
   - 13 个属性都没有定义域或值域；
   - 生成器自己定的「成员定义开头的字面等式转 hasValue」规则，在 H05 的 4 个类和 H04 的「城市」上没有生效；
   - 推理只能证明它「不矛盾」：本体里几乎没有可推理的实例，所以这个结论偏弱。
2. **有没有「本来能拿到的提升没拿到」。**
   - 写错：唯一一条不一致的是 E07，形式部分丢了「蓝色筛选不分大小写」这个条件。但题库里没有一道题的参考答案按蓝色（或任何颜色值）筛选，这个错误在本题集上影响不到任何题。所以没有「会误导模型、而且涉及 L3a 答错的题」的错误。按事先登记，**不需要修正后重跑**。
   - 写得浅：79 条注解保留的条目里，16 条有现成的 OWL / SHACL 写法。按事先登记的规则，它们涉及 32 题（主表 29 题）。L3a 在其中 14 题上至少错一次，5 题三次全错；L1+ 在同样的 32 题上错 13 题。这是交给 L3b 的输入清单，不是提升的估计。
3. **本体能不能校验语义层和数据。** 能，但要另写 shape，L3a 自带的 shape 做不到。用修正前的父子列加上三类最少量的 shape：
   - 查出了科目树环（节点 1、24）和员工汇报链环（节点 1、18）；
   - 查出了 FactOnlineSales 的 284 个孤儿 ProductKey，共 **1,715,380** 行，与 T24 一致；
   - 查出了 ColorName 的 Blue（148 行）/ blue（2 行）。

   在 22 个文本列、4 组外键、3 棵树上，**没有查出之前不知道的问题**。这只说明本体「能」查出这些问题，不说明它「会」主动发现：shape 是对着已知问题写的。

## 3 建模检查

逐条对照 `semantic/l1plus.yaml` 原文（判定标准：形式部分有没有说出原文没说的、或与原文相反的东西）。逐条核对的明细见 `model.json`：
- 别名：每条映射的标签 = 说法，:value = 取值，:column = 列，没写进形式部分的字段；
- 层级：子类方向、成员定义有没有转成 shape、shape 的取值、关系的定义域和值域、科目树的父子边。

## 6 本体不够好、错过了提升？（只用现有日志）

- **事先登记**：映射规则、计数口径和可形式化清单，都在看到逐题结果之前提交了，见 `scripts/t26/preregistered.py`，提交 c64f4f1。
- **映射规则**：条目的「签名」正则（只认该条目自己的列、表或字面量）命中某题任一参考 SQL，就算该条目涉及这道题。题目如果走的是别的列（例如用 toMonth(DateKey)，没有用 MonthNumber），不计入。
- **日志与口径**：日志是 `20261025-T22b-l1plus-l3a-03-rescore-01`（v2 最终判定）。「答错」= 3 次里至少 1 次不对，「全错」= 3 次都不对。
- **核对**：总数与 T22b 一致。L3a 在 109 题上对 240/327 次，至少错一次的有 43 题；L1+ 对 245/327 次，至少错一次的有 38 题。

### 6.1 写错

第 2 步没有发现问题，第 3 步唯一不一致的是 E07。

| 条目 | 涉及题（109 / 主表 98） | L3a 答错 | L3a 对 / 次 | L1+ 答错 | L1+ 对 / 次 |
|---|---|---|---|---|---|
| E07 | 13 / 11 | 5（Q61、Q67、Q71、Q73、Q98），其中全错 2（Q71、Q98） | 29/39 | 5 | 30/39 |

补充核对（机械检查，在映射之后做的）：这 13 题的参考 SQL 没有一份出现 `blue`，也没有一份对 ColorName 用 lower()。L3a 和 L1+ 在这些题上的作答也都没有出现 `'blue'`。也就是说，E07 丢掉的那个条件在本题集上没有一道题会用到，**它解释不了这 5 题的错误**。L3a 在这些题上比 L1+ 少对 1 次，在三次重复的波动范围内。

E09（拿不准）作参考：涉及 4 题（Q18、Q66、Q69、Q78），L3a 和 L1+ 都是错 2 题（Q18、Q69），9/12 对 10/12。

**结论**：没有「会误导模型、而且涉及 L3a 答错的题」的错误。按事先登记，不触发修正后重跑 SQL-L3a。是否仍要修正 E07 的编码，由用户决定。

## 局限

- 「逻辑一致」只在 OWL-RL 下验证过，没有跑 DL 推理器。本体几乎没有实例和类公理，一致性检验很容易通过。
- 第 3 步的「一致」只说明形式部分没有与原文相反，不说明它表达了原文的全部内容。L3a 的设计是全部原文放在注解里，模型实际读到的也包括这些注解。
- 第 6 步的签名是按列名做的机械匹配，可能多算（例如 A40 用品类名作签名，任何按品类分析的题都会命中），也可能漏算（题目改走别的列）。
- 第 5 步的 shape 是对着已知问题写的，结论只能写成「能查出」，不能写成「会主动发现」。
