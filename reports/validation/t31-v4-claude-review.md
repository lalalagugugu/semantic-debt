## 方法

1. **独立实现**：检查脚本 `scripts/review_v4_flips_claude.py` 由本会话从零写成，没有 import 或复制 `scripts/t31_*.py`，没有读 Codex 的中间产物（`candidate-rules.py` 快照和 `index.json` 里的 `candidate_content_correct` 都没有用）。每次作答只读 `answer-result.json`、`reference-results.json`、`question.json`、`hit-rules.json` 四个文件。命中的规则只当作待验证的主张。
2. **只放开命中的规则**：基线与 v2 相同（相对 0.5%；按值类型的绝对下限：金额 0.01、比率 0.0001、百分比 0.01；比率类允许 ×100 / ÷100；多余的作答列不管；参考无序时不看行序；参考 NULL / 空分类名可匹配一个不与其他成员重名的文字标签，这是 v2 已有的规则）。每条规则只解锁它自己的变换：
   - R1：两边的期间各自解析成（粒度、年份或无、序号）。只接受无损写法：英文月名、`YYYY-MM`、月首日期、季首日期（列头为季度时）、`YYYY Qn`、`Qn`、`Year YYYY`、四位年份文本，以及年份列和月 / 季列的拆合。粒度必须相同。一边有年份、一边没有时，**只在题面恰好出现一个年份、且有年份的一边等于这个年份**时才算相等。
   - R2：参考的长表按枚举值转成宽表，每个枚举值必须恰好对应作答的一个数值列头。作答里能识别的差额 / 差异率列逐行核对 = 实际 − 预算、÷ 预算。
   - R3 / R8：把参考的名、姓合并成「名 姓」或「姓 名」；只有名或姓是占位值（`Not Provided`）或缺失时，才允许作答在名称列里给该行的实体编码。R8 只在参考名称逐行唯一时才允许省略编码列。
   - R4：只去掉作答分类值末尾的「客户 / customer(s)」，行仍须一一对应，不能把不同状态合并。
   - R6：列头含「减少 / 下降 / 降幅 / 缺口 / decrease…」的列才允许取负。
   - R7：只在题面不含排序 / 名次 / 前 N / 最高最低等字样、且没有 Top-N / selection 时才忽略行序。
   - R9：参考中取值恒定的总额列只能在「某个分组金额列的合计 = 总额」时省略，而且这个分组金额列必须在作答里逐组对上。
   - R10：折前额必须能由折后营收和折扣率逐行还原（折后 ÷ (1 − 折扣率)），两列都必须在作答里对上。
   - R11：作答必须有一行包含全部比较指标，并且能由比较组和基准组两行逆算出差额和百分比。
3. **匹配**：先给参考的每个必答列找候选的作答列（列名不参与），再按「全部映射列同时相等」做行的一对一最大匹配（不做笛卡尔积）。参考是 Top-N 并列候选池时，名次严格落在 N 以内的行必须全部出现，每组行数必须够。参考有序时，按参考排序键逐行核对（并列内的顺序不限）。名次列按 v2 规格第五节第 9 条接受竞赛、稠密、位置编号三种写法，并核对位置编号落在参考的并列块里。
4. **空值**：数值 NULL 不等于 0，没有例外。
5. **人工复核**：脚本自动确认了 285 次。另外 18 次（都是 Q88）因为名次写法与参考不同而停下来等人工看，人工逐条核对后的结论记在 `reports/validation/t31-v4-claude-review-manual.csv`，由脚本合进最终附表。除此之外，我按题号核对了每题实际用到的列映射和变换，并对每条规则至少逐行看过一份原始作答，重点是 R1 的年份推断和 R3 的编码回退，没有发现借变换放过内容差异的情况。
6. **自检**：`tests/test_review_v4_flips_claude.py` 用合成数据（不含真实题目和结果）验证脚本会拒绝以下情况：超出容差、数值 NULL 当成 0、题面有多个年份时推断年份、没命中 R1 就做期间转换、题面要求排序时用 R7、真实姓名换成编码、没有减少量列头就取负。

## 重点：SQL-L1plus 的 Q88 第 1、2 次（行 291、292）

结论：**放行正确**。

- 内容：前 20 名的客户集合、顺序、全年消费额都与参考一致。参考第 20 名有 7 人并列，作答各取了其中一人（r1 和 r2 取的不是同一人），都在并列候选池内，第 20 名之前的必含行全部出现。
- R3 的适用：第 1 名客户的名和姓都是占位值 `Not Provided`，作答在名称列里给了它的客户编码，同时保留了编码列。系统提示第 6 条原文是「名称缺失或是占位值时给编码」，R3 允许的也只有这一种回退。其余 19 行都是真实姓名合并，逐行一致。
- 名次列：作答按位置编号（3、4、5…），参考用竞赛排名（并列者同为 3）。v2 规格第五节第 9 条明确接受位置编号，所以这不是改判的理由，v2 判错只因为名称。
- **为什么两家早先的归因没标「只是呈现不同」**：我看了源日志里这两次的最终查询，两次都加了 `SalesQuantity > 0`，即只算有正销量的行。L1plus 语义文档把「购买」定义为包含只有退货行的交易，所以归因方标成「文档写清楚了，模型理解偏了」是看 SQL 口径得出的，合理。但这个口径差异在本数据上没有改变前 20 名或金额，结果与参考逐行一致。按 10-26 裁决「查询结果在内容上回答对了问题即算对」，结果层面放行是对的。
- 同一题其余 16 次 R3 放行（行 61、62、109、130、131、150、151、174、175、198、223、229、243、244、245、262、327）情况相同：都是占位名给编码、名次按位置编号。其中行 62、109、131、151、223、243、245 的查询同样只算正销量，结果也不变。

## 需要用户知悉的解读（不改变结论）

1. **只看结果、不看 SQL 口径（Q88 共 9 次）**：上面这几次是查询口径偏离文档默认，但结果碰巧不受影响。按现行裁决，准确率只看结果，所以放行。用户如果认为「口径错、结果对」不该计入准确率，这是一条超出 v4 规则的口径（v2 本身也只看结果），影响行 62、109、131、151、223、243、245、291、292。
2. **R2 的中文列头（Q31，11/15 次）**：作答列头是「实际…」「预算…」，参考的枚举值是 `Actual` / `Budget`。我只用语义层自己写明的对应（`semantic/source.yaml` 场景列：「1 = Actual（实际）、2 = Budget（预算）」）来识别，没有做自由翻译。若用户认为这也算「需要翻译」，这 11 次退回原判。
3. **R1 由题面年份补齐 / 省略年份（98 次，Q12、Q23、Q64、Q66、Q77、Q113）**：题面都只写了一个年份（Q12 是 2008，其余是 2009），参考或作答有一边不带年份。题面有多个年份的题（如 Q16、Q72、Q90、Q110）没有用这条，年份都是两边逐行对上的。
4. **季首日期当季度（Q66，JSON-L2 3 次、SQL-L2-notes-v12 1 次）**：列头写明是季度，值是 `YYYY-01/04/07-10-01` 这样的季首日期，这与 T23 已接受的月首日期同类，属于无损写法。JSON-L2 的数值以文本形式返回，按数值比较（v2 同样如此）。
5. **Q90（行 200）**：参考里品类为 NULL 的一组，作答给了「未知品类」。这一点由 v2 已有的 NULL 名称规则判等，不是 R5；v2 判错只因为年份标签。
6. **Q112（行 37、201，R8）**：作答省略了经理编码列，经理姓名在参考中逐行唯一。参考里有一位经理姓名为空，作答给了这位经理的编码，属于第 6 条的回退，逐行一致。
7. **Q50 / Q104（R6）**：题面问「增长了多少」，作答用「减少额」列给正数，同时给了负的变化率；方向由列头表达，金额一致。
