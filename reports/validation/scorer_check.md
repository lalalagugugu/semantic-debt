## 方法

1. 单进程打开 `chdb-eval`，先重算 99 份可用参考结果，再执行 6 × 100 条候选 SQL。
2. Top-N 参考 SQL 用 `WITH TIES` 扩展，确保参考结果包含完整边界并列组。
3. 使用 `harness/scorer.py` 的冻结规则评分，与公开 strict 和 analytical verdict 逐条比较。
4. 报告只保留系统代号、题号和归类，不保存题目或 SQL。

复现命令：

```bash
uv run pytest tests/test_scorer.py
uv run python scripts/validate_scorer.py --output /tmp/t02-scorer-check.json
```

系统代号：O-R = Opus raw，O-S = Opus semantic，S-R = Sonnet raw，S-S = Sonnet semantic，G-R = GPT-5.4 raw，G-S = GPT-5.4 semantic。

## Strict 不一致

### 我们更宽（18）

- 边界并列（3）：G-R Q07；O-S Q27；S-S Q27。完整边界组证明候选所选成员与第 N 名同值，符合冻结规则。
- 小数/百分数等价（7）：O-R Q96；O-S Q96；S-R Q37；S-S Q64；G-R Q96；G-S Q64、Q96。
- 0.5% 数值容差（1）：S-S Q83。候选计数相差 1，仍在冻结容差内。
- 本地重执行与公开结果工件不同（7）：六个系统的 Q14；G-R Q30。Q14 的候选 SQL 与参考 SQL在本地完整结果上等价，但公开保存的前 100 行互不一致；Q30 在当前 chDB 重执行后通过 0.5% 比对，但公开 judge 基于旧执行结果判错。这 7 条不是评分器放宽规则造成。

### 我们更严（61）

- 缺少参考列（28）：O-R Q32、Q70；O-S Q32、Q63、Q66、Q70、Q81、Q83；S-R Q32、Q35、Q70、Q81；S-S Q35、Q63、Q66、Q70；G-R Q22、Q32、Q63、Q83；G-S Q63、Q66、Q69、Q77、Q78、Q81、Q83、Q84。公开 strict 把参考 SQL 中“未被问句要求”的列忽略了；冻结规则要求参考每一列都找到匹配列。
- 候选多行（9）：O-R Q80；O-S Q45、Q75；S-R Q45；S-S Q75、Q80、Q92；G-R Q45；G-S Q92。候选返回完整明细、完整国家集或多一条边界行，公开 strict 只核对前 N/核心子集；冻结规则要求完整结果集，且 Top-N 候选必须恰好 N 行。
- 物理行序（2）：O-R Q22；O-S Q22。题目要求分组 Top-N，冻结规则比较行序；公开 strict 忽略排序。
- 字符串标签或列组合不同（14）：O-R Q35、Q64、Q88；O-S Q35、Q88；S-R Q88；S-S Q88；G-R Q68、Q88；G-S Q23、Q26、Q68、Q72、Q88。公开 strict 接受拆分/拼接姓名、数字月份与文本月份、枚举标签改写；冻结规则只做字符串首尾空格归一化。
- 参考度量缺失但候选列数不少（3）：O-S Q90、Q95；S-S Q82。候选用其他额外列替代了参考度量，公开 strict 接受核心子集；冻结规则不接受。
- 外部 `<1%` 与本项目 `0.5%`/未约定舍入不同（3）：S-S Q24、Q99；G-S Q29。
- 本地 chDB 函数不兼容（2）：G-R Q08、Q59。候选使用的 `lowerUTF8` 在当前 chDB 返回 `UNKNOWN_FUNCTION`，公开运行环境执行成功；评分器按本地执行态记 `exec_error`。

上述 61 条均是公开 strict judge 比冻结规则更宽，或执行环境不同；没有理由为提高一致率而改动冻结评分规则。

## 结论

评分器按冻结规则工作，所有最终差异均已逐条归类。但公开 strict verdict 的实际口径明显宽于其报告描述，也宽于本项目冻结规则，因此 **T02 当前未满足“排除有意更宽后 strict 一致率 ≥95%”的验收项**。进入 G0 前需用户裁决验收口径，不能通过修改评分器追分。
