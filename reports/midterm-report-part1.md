# 智能问数实测·上：同一个大模型，准确率从 48% 到 93%，差在哪

2026-11-09 · Yu HUANG

## 要点速览

想要自然语言问数，把语义交代清楚是回报最明显的一项投入。同一个大模型，从低质量的语义说明换成内容完整的版本，准确率从 48.0% 提升到 85.0%。之后有两条路线：独立盲审、逐条消歧并补充常用概念，到 93.2%（全部 98 题）；上线后按错答复盘，在测试集（49 题）上到 92.5%。

- **语义层是一份写清业务含义的文字文档，不需要额外买产品。** 内容是业务名、表与表的关系、字段和枚举值的含义、企业自己的约定、指标的算法。先把这份文档写完整，再考虑其他的投入。
- **独立盲审语义层能暴露歧义。** 换一个人或另一个 AI 对着干地审，比顺着读的检查更能找出歧义。本实验开发指标层时把 69 个口径（指标的算法定义）写成代码，就暴露出 14 处能读出不止一种算法；之后不看题、逐条盲审整份 L1的语义说明（15 条约定、69 个指标、48 条关系、25 个数据集的使用说明），消歧并补充常用概念，补了 109 条之后，准确率从 85.0% 提升到 93.2%。
- **上线后按错答复盘，复盘时没用过的题（测试集）上也更准。** 通过复盘进一步消除语义层歧义，测试集上的准确率从 85.0% 提升到 92.5%。因此上线后要留出持续复盘的人手，并有人负责统一口径。

## 实验过程说明

每组对照只换一类东西，其余固定：同一个大模型、同一份数据、同一套题。每种做法算一个「测试单元」，本篇共涉及 7 个测试单元（下篇 21 个），列在附录。语义层是给大模型看的说明，告诉它表和字段是什么意思、指标怎么算；指标的算法定义下文称为「口径」。

**数据是微软的零售数仓样例 ContosoRetailDW。** 25 张表、244 个字段、约 3,400 万行。

**题目是 98 道计分的中文问题。** 76 道改写自 Cube.dev（一家做语义层产品的公司）发布的公开基准，22 道是按公开题缺的场景新写的（业务说法、相近门店名、企业约定、计划与实际、客户派生属性、多步计算等）。难度分三级：

- 一级（最低）38 道，如「2009 年的线上销售额是多少？」；
- 二级 33 道，如「2009年比2008年营收增加但毛利减少的产品品类有哪些？各自两项金额变化是多少？」；
- 三级 27 道，如「在2009年同店销售下降的门店中，降幅最大的3家门店各自由哪个产品品类拖累最多？列出门店降幅、该品类销售减少额及其占门店总减少额的百分比。」

**被测大模型是 DeepSeek-V4.1-Flash-1017，开启思考模式。** 大模型直接写一条 SQL，在 ClickHouse 上执行；执行报错时把报错发回，允许修一次。每种做法 98 题各答 3 次，全部计分。写语义层的和出题、判分的不是同一个 AI，分工见附录。

**调优集和测试集。** 98 题事先按难度、面向对象（管理层 vs 数据分析师）和题型组合分层，每一层里的题平均分到两边，合起来调优集和测试集各 49 题。语义层的调优只在调优集上做，把调优集当作上线后收到的问题；测试集用来判断所做的调优能否推广。语义盲审不看题。

**大模型的作答是否准确只看内容**：查出来的数回答对了问题，就算对。「2023-01」和「2023 年 1 月」、百分数和小数、长表和宽表都算对。Cube 公开基准的主要评法也接受这类差异。本实验另算了要求格式也一致的评法，本篇各单元在这种评法下低 4.1–17.3 个百分点，见附录。

**如何解读不同单元之间的准确率差异。** 每个单元只有 98 道题，重跑一遍数字也会变。比较两个单元时逐题比，排除题目难易的影响。差距大到不太可能只是随机波动时（差值的 95% 置信区间不含 0），本报告称为统计显著，写「显著更高」或「显著更低」；否则写「差异不显著」并给出差值。**不显著不等于没有差别。**

## 1. 语义说明的质量决定问数准确率：同一个大模型，48.0% → 85.0%

提示词不变，只换语义说明，准确率显著更高（差值 +37.1 个百分点）。L0 模拟的是交付质量低下的语义层：命名晦涩、没有描述、表关系不全，用来看语义层交付得差时，问数能做到什么程度。

| 测试单元 | 给大模型看的语义说明 | 准确率 |
| --- | --- | --- |
| L0 低质量语义层 | 晦涩的表名字段名、没有描述、只给约三分之二的表关系、技术字段也暴露 | 48.0% |
| L1 内容完整的语义层 | 业务名、全部表关系、字段描述、枚举含义、同义词、企业约定、69 个指标的文字口径 | 85.0% |

L0 上大模型写得出 SQL，业务含义只能猜。一些信息从数据里看不出来，只有业务方知道。比如在这份数据里：

- 「我们有多少家门店」要不要算网店？库里有 7 家虚拟门店。
- 「线上销售」包括哪些渠道？
- 「订单数」算不算只有退货的订单？

同样两个字段，在两份说明里长这样。L0（大模型只看到表名、列名、类型）：

```text
d_cst.gdr      Nullable(String)
fct_ol_sls.amt1  Float64
```

L1（摘自语义层源文件）：

```yaml
- name: DimCustomer
  columns:
    - name: Gender
      description: 客户性别，单字母码。注意 DimEmployee.Gender 写的是全词 Male / Female，两张表的写法不一致。
- name: FactOnlineSales
  columns:
    - name: SalesAmount
      description: 销售金额（美元），已扣折扣、未扣退货（约定 7）。退货行上这一列是 0。
```

L0 上大模型猜不出 gdr 是性别、amt1 是已扣折扣未扣退货的销售额，L1 里这些各是一句话。

## 2. 语义层是一份文字文档，内容要覆盖完整，只给表结构不够

**语义层不需要专门的产品。** 本实验的 L1 就是一份 YAML 格式的文字说明，内容分七类（例子都取自 L1 原文）：

| 写什么 | 例子 | 不写会怎样 |
| --- | --- | --- |
| 业务名 | DimProduct → 产品、SalesAmount → 销售额 | 大模型从字段名猜含义 |
| 表与表的关系 | 销售表通过产品键关联产品表 | 关联路径选错，数重算或丢行 |
| 字段描述 | 销售金额已扣折扣、未扣退货，退货行上这一列是 0 | 销售额和净销售额算混，数算得出但口径不对 |
| 枚举值的含义 | 客户表性别写 M / F，员工表写 Male / Female | 筛选条件写错，查出空结果 |
| 同义词 | 「客单价」「平均订单金额」「平均客单」「AOV」是同一个指标 | 问法一变就找不到对应的指标 |
| 企业约定 | 「门店」默认含不含网店、「线上」包括哪些渠道 | 大模型只能猜，可能每次猜得不一样 |
| 指标的算法 | 复购率的分子分母、取哪个时间窗 | 算法各异，结果看起来都对 |

**解题要靠本公司业务知识的题，最需要把这些写下来。** 98 题里，解题要靠所属公司业务知识的 78 题，L0→L1 差值 +43.2 个百分点，显著更高；靠常识和数据就能解的 20 题，差值 +13.3 个百分点，差异不显著。

**只给表结构不够。** 只给原始表结构（业务原名，即测试单元 R）时，大模型的作答准确率是 51.7%，和低质量语义层（L0）差异不显著（差值 +3.7 个百分点）。

**语义文档也有交付质量之分：同样写了约定，内容覆盖的完整性可以差很多。** L1c 是 Cube 公开基准自带的文档，准确率 68.7%，比 L1 显著更低（差值 −16.3 个百分点）。

| 内容 | L1c | L1 |
| --- | --- | --- |
| 指标口径 | 13 项 | 69 项 |
| 枚举含义 | 两张小表共 11 行 | 77 个字段逐个取值写了含义 |
| 同义词 | 没有清单 | 56 组 |
| 写给 agent 的操作规则 | 13 条 | 拆到了系统提示词的作答说明、写法说明和语义说明里 |
| 系统提示词长度（token） | 约 6,800 | 约 46,500 |

下面两组写法，左边是 L1c 原文，右边是 L1 对应的写法，L1 也写明了表和字段。第 1 行在 L1 里没有歧义；第 2 行即使在 L1 里仍有歧义，第 3 节展开。

|  | L1c 原文 | L1 的写法 |
| --- | --- | --- |
| 1 | `AccountKey = 50`；Sales Amount account（销售额科目） | `DimAccount`：`AccountName` = `Sale Revenue`（`AccountKey` = 4），即销售收入科目 |
| 2 | 同店：compute ONE scalar % change, restricted to stores that had sales in BOTH compared years（只算一个变化百分比，限于两个对比年份都有销售的门店） | `FactSales`，`sum(SalesAmount)`：只统计两个对比年份都有销售的门店；同店销售额增长率 =（同店本年销售额 − 同店去年销售额）÷ 同店去年销售额 |

**企业现有的语义文档也不能当金标准，要对着数据核验。** 第 1 行就是 L1c 的事实错误：这份数据里没有科目键 50，正确的是 4。

**本实验的结果和公开基准方向、幅度一致，说明实验过程可靠。** 本实验 R→L1c 是 51.7%→68.7%（差值 +17.0 个百分点，显著更高）；Cube 公开基准里三个前沿大模型不用语义层时是 46–51%，用上语义层则到约 68%。

## 3. 语义层写得准不准，要看同一个口径能不能实现成唯一一种算法

**写口径的人心里只有一种读法，自己看不出歧义。** 本实验精心准备、认为已经写清楚的 69 个口径里，有 14 个能读出不止一种算法。第 2 节对照表里的「同店」，就是其中之一。L1 里「同店」的口径是一句话：**两个对比年份都有销售的门店**。这句话有两处能读出不同的算法：

| 含糊处 | 读法一 | 读法二 | 最后定为 |
| --- | --- | --- | --- |
| 「有销售」 | 那一年至少有一条销售记录（含纯退货订单） | 那一年销售额合计大于 0 | 至少有一条记录 |
| 「对比年份」 | 按整年判定 | 按问题里对比的那个季度或月份判定 | 按整年 |

两种读法算出来的门店集合或者对比区间不同，同店销售额也就不同。文档不定下来，大模型每次都可能选的不一样。

**把文字口径独立实现成代码再逐条对账，就能暴露歧义。** 搭指标层时，另一个 AI 会话把 69 个文字口径写成指标代码，再和文字逐条对账，就意外发现「写」清楚其实只是「自以为」。因此，本实验做了一轮不看题的独立盲审，逐条审整份 L1，问「这句话能不能读出两种算法」，补了 1 条通则（适用于所有比率的规则）、41 处澄清、37 个常用派生概念（如复购率、日均销量）、17 个别名（同一事物的其他叫法）、13 组层级（如科目的上下级），得到 L1+：

| 测试单元 | 准确率（全部 98 题） |
| --- | --- |
| L1（内容完整的语义层） | 85.0% |
| L1+（完整且逐条消歧的语义层） | 93.2% |

**请另一个人或另一个 AI 做独立盲审：把核心指标独立写成 SQL，和业务负责人默认的算法逐条对比；AI 能找出歧义，但具体按哪一种方式解读，还要业务方定，定下后写回语义层。** 本实验这样消歧并补充常用概念之后（L1+），准确率显著更高（差值 +8.2 个百分点）。

## 4. 上线后按错答复盘，没见过的题也会答得更准

**盲审无法****查全歧义，上线后还会冒出文档里自相矛盾的口径。** 复核 L1 错答的题目时，又发现「日均销售额」这个指标默认用全渠道的销售表，而同一份文档的另一条约定写的是「没说渠道就指线上」。两条规则自相矛盾，但盲审没有查出来。

所以上线后还要按错答复盘。本实验把调优集当成上线后暴露的错题用于复盘，补了两类东西：**补语义**（口径澄清、企业惯例、示例 SQL）和**补作答要求**（大部分是格式，少数是 SQL 语法的避坑）。下面只看复盘时没看过的测试集（49 题）：

| 做法 | 准确率 |
| --- | --- |
| L1，没有复盘 | 85.0% |
| L1+，独立盲审消歧 | 93.2% |
| 复盘补语义 | 92.5% |
| 复盘补语义 + 作答要求 | 93.2% |

复盘补语义在测试集上的准确率显著更高（差值 +7.5 个百分点），说明复盘补语义对复盘时没见过的题也有用。再补作答要求，差异不显著（差值 +0.7 个百分点）。上线之后还要做三件事：

1. **持续监控，继续消除剩余歧义。** 复盘修好了看过的题，没看过的题还会遇到文档没写死的读法。本报告认为，第 3 节和本节的两种办法每做一轮都会再找出一些，**口径的统一可能没有尽头。**
2. **新补的口径要先和已有内容对账，只留一种读法，最好有一个口径负责人。** 纸面上的说明越多，越可能互相打架：本实验分开做的盲审和上线后复盘，各自补的内容有 17 处互相矛盾。
3. **在数据层解决数据质量问题，不要指望文档兜底。** 这份数据里：线上销售表 14% 的行关联不上产品；Blue 和 blue 并存；科目树和员工汇报链有成环；客户姓名等关键字段有占位值——在没有解决这些问题的情况下，本实验是靠文档做解释性兜底。数据标准化之后，文档也可以更简单。

## 本篇的局限

- **只测了一个大模型、一份公开数据、98 道题。** 不同测试单元之间的相对关系没有在别处验证。
- **约四分之一的判定靠 AI。** 确定性代码和规则判不了的约四分之一作答，由 AI 逐次判定；AI 判为正确的，有一部分由另一家 AI 复核；判为错误的，只在早期抽查过一部分。
- **语义层的投入没有算进来。** 本实验里由 AI 写语义层（L1 记录的会话耗时约 3 小时）、AI 找歧义、实验者裁定就够了；真实企业里不管人还是 AI 起草，都要各业务方和数据负责人讨论拍板，需要的投入和协调要复杂得多。
- **复盘时错答全部已知。** 本实验把调优集的错答全部拿来复盘；但上线后的错答要靠抽核和点踩发现。

下篇讲换技术能不能绕过写语义这件事：会查库的 agent、本体、指标层和汇总表，以及上线后怎么兜底。

### AI 工具分工

Claude Code（Opus 5.5）：看不到题的条件下写语义层和指标代码，写实验框架并运行，用 pandas 独立重算参考答案，复核判定，起草报告。

Codex（GPT-6.1 Sol）：出题和参考答案，评分器，部署指标层并跑相关单元，逐次内容判定和数字复核。

早期用过 GPT-5.6 和 Opus 5（评分器初版、项目骨架）；工具内置的联网搜索、网页解析可能涉及其他模型。

### 怎么判分

**参考答案的口径来自业务方。** 真实项目中，参与调研的业务方心里有一份认可的答案，这份答案就是企业的内部定义，参考答案的口径由它而来；文档没写死、但不在业务方认可的读法里的作答，判错。判定规则里有一部分是看过各单元抽样出的错例之后才补的，和真实项目一样：业务方指出结果不对，才发现口径有差异，再把说明补回语义层。

每次作答依次过三步：

1. 确定性代码对参考答案，内容和格式都对的直接通过。
2. 11 条确定性规则认可「只是呈现不同」的作答。
3. 剩下的作答全部由 AI 逐次判定内容对不对，不抽样。

逐次判定遵守三条原则：

- **A：参考答案代表企业的真实口径。** 作答所在单元的文档没有写死某个口径，作答选了另一种读法，判错。这种就是要靠持续消除歧义。
- **B：漏掉「未归属」组，判错。** 漏掉这一组，合计就对不上。
- **C：作答遵守了它看到的文档里的明确规则，而参考答案与该规则冲突，判对。**

另有几条统一规则：

- 所缺的数能由作答已列数字一步算术、无歧义得到，且作答没有给出矛盾的结果，才算内容正确；需要多步跨期累计的判错。
- 空值不等于零；所问的格直接为空值判错，不能靠旁列补救。
- 列名写明百分点或百分比、数值却差 100 倍，判错。
