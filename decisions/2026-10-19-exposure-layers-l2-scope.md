## 一、看问题的角度：把数据暴露到哪一层

本实验的初衷是「做 AI 问数时，先做数据治理（补语义层），还是先做强 agent」。汇总层、指标层对多数公司是既有资产，问数项目开工时不会为此新建；工程上真正的选择是**暴露给 agent 的入口与退路**。现有单元按暴露面排列：

| 暴露给 agent 的东西 | 单元 |
|---|---|
| 只有指标，只能调用（可任意组合已定义的指标与维度，不能在结果上再算） | JSON-L2 |
| 只有汇总层（ADS） | L1.5S |
| 指标对象，可在结果上再写 SQL | SQL-L2 |
| 指标对象 + 探查 | SQL-L2-E（T15） |
| 明细 + 文档（+ 宽表） | L1、L1.5W |
| 明细 + 探查 | L1-E |

报告（T19a、T19）按这个角度组织 L2、L1.5S 的结论。

## 二、L2 交付范围：只补 L1 已承诺的，不补新口径

T16 把 JSON-L2 冒烟的 10 条拒答分为 ①「常用指标交付不足」9 条、② 接口组合限制 1 条，并建议 9 个指标口径。

1. **M-SHARE（销售额占比的父组分母）进 `semantic-v1.4`**：L1 原文已承诺「分母的范围由问题决定（全公司、某渠道、某品类内）」（`semantic/source.yaml` 销售额占比条），Cube 只实现了全公司，属于 L1 → L2 编码不全。不按某一题修，而是 v1.4 加一项**通用检查**：逐个核对 69 个指标，L1 写明的范围或变体在 Cube 与 DAX 上是否都实现；缺的照 L1 文字补实现，不改 L1 文字。结果并入 DAX vs Cube 对照表，Codex 复核。
2. **其余 8 个（M-RANK、M-QUANTILE、M-AREA、M-STOCK、M-REPEAT、M-SPAN、M-COHORT、M-HR）本期不进语义层**：它们是 L1 没有的新口径，从具体题的拒答反推而来；加入要先改 L1，违反「不按题调」（硬规则 3）和「L2 只编码 L1」（`semantic/metrics.yaml` 头注），并使已跑完的 L1 系列单元全部要重跑。
3. **拒答与失败的报告口径**（SQL-L2、JSON-L2 都适用）：(a) L1 也没写的口径（交付范围外）；(b) L1 写了、L2 没编码（v1.4 修的缺陷）；(c) 接口表达不了；(d) 只因展示约定的必答列（如名次、增长额）而答不出。四类分开报，不混进准确率去解释。

## 三、JSON-L2：跑一个单元的全量；取消 3 级

1. **取消 JSON-L2 · 3 级**（取代 l15s-reporting 裁决第二节）。v1.4 待办中的「JSON-L2 · 3 级说明」一并拿掉。
2. JSON-L2（2 级说明，`semantic-v1.4`）跑一个单元的全量，跳过 judge 题，每题 3 次；开跑前 dry-run、用户批准预算（约 6 元）、错峰。
3. **开跑前**由 Codex 做静态的指标层覆盖标注（只记题号与类别，在主仓库提交、以提交号固定）：主表每题能否用现有成员（含 v1.4 补的父组占比）一条 JSON 答出；答不出按第二节 (a)–(d) 归类；能答出的，记下所需的指标与维度成员（「标准成员集」）。
4. **主比较口径**：在 JSON 能答（未拒答）的题上，SQL-L2 与 JSON-L2 同题配对比较正确率、错答率、执行失败率；JSON 拒答的题上另报 SQL-L2 的表现。冒烟时的读数（13 题 × 1 次，只作方向）：SQL 8 对 4 错 1 失败，JSON 6 对 6 错 1 失败；JSON 对、SQL 错的题为 0。
5. **JSON 错因拆分**，按机械规则，不靠事后判断：
   - 执行报错 → 写法或接口问题（指标放进维度、维度放进指标这类位置错误，Cube 会直接报错，落在这一类）；
   - 执行成功但所选成员与标准成员集不同 → 选错指标或维度；
   - 成员相同、结果不同 → 指标实现的读法与参考不同，或形状/展示约定问题。
   冒烟里四题的初步核对（协调会话读日志所得，待 T16 逐题确认）：Q17、Q69 的 JSON 作答与 SQL 选的指标、维度相同，错在数值，不是选错或写错（具体原因待 T16 对数值）；Q50 选对了同店指标，错在只能按年分行、给不出增长额（第二节 (d)）；Q34 选对了库存周转率，两轮都错加了销售日期筛选导致跨事实表连接失败（写法问题）。
6. Cube JSON 查询格式是 Cube 公开、开源的接口（`/load`），不是本实验自创；本实验只写了说明（`render/syntax/cube_json.md`，2 级，含一行格式骨架，骨架按 self-built-p 裁决第五节第 5 条保留，在 `semantic-v1.3` 中）。成员名是本实验的 Cube 模型。

## 五、回退链（记录，供最终报告引用）

用户的观察与协调会话的回应（未联网核实，报告引用前须核对）：

1. 通常不把各层平铺进同一个上下文。常见做法是只给 agent 一小组精选的表或一个语义模型；表越多、含义越重叠，越容易选错表。本实验的旁证：L1.5W（宽表叠在明细上）无增益；L1.5S 在单层内已有一半失分来自选错表。
2. 更贴近现实的是**有序的回退链**，逐级放宽表达力：
   1. 指标 API（只能调用已定义指标）→ 对应 JSON-L2；
   2. 在指标结果上做临时计算（SQL over 语义层）→ 对应 SQL-L2；
   3. 退到明细表写 SQL → 对应 L1 / L1-E；
   4. 退到 Python（统计、多步计算）→ 对应 -P（第二期）。
   每退一级，覆盖面变宽、可治理性变弱、错答风险可能变大。报告可以按这条链读各单元。
3. **第二期候选单元：「指标层优先 + 明细退路 + 探查」**：agent 同时有 Cube 接口与明细 `run_sql`，自己决定何时退。第一期没有这个单元（SQL-L2-E 只能查 Cube，看不到明细表）。放第二期的理由：需要两个执行后端和新的工具说明冻结（`harness-agent` 新版本），且 v1.4 尚未定稿；第一期已有回退链各级的单点。是否加入第二期，由用户在第二期规划时定。
