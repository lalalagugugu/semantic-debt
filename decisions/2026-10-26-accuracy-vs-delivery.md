# 2026-10-26 「准确率」只算内容；交付约定单列「按约定交付率」

- 裁决人：用户，2026-10-26（「分开汇报『准确率』和『按约定交付率』，这个对于调优补丁影响的几个单元也同样做分别汇报」；原则：交付约定「应该是用户体验的锦上添花，它的影响不应该影响准确率，如果它影响准确率，那就是我们的准确率统计口径有问题，应该拆分开来」）
- 起草：协调会话；合并即确认
- 修正：`decisions/2026-10-18-names-required-by-system-prompt.md` 第二节第 2 条、`decisions/2026-10-18-ux-conventions-and-annotation-disputes.md` 第一节第 2 条（体验类约定成为必答列）——约定本身保留在系统提示里，但不再计入准确率
- 约束：T31（第二部分产出改为两套口径的规则）、T29（筛选结论两种口径都算，见 `decisions/2026-10-26-t29-expanded-pilot.md` 的追加登记）、T20、v3 中期报告、终版报告

## 一、为什么改

1. 10-18 两份裁决把系统提示「结果的写法」第 6–15 条（名称标识、每组一行、不加合计行、期间写法、变化给绝对值和百分比、名次列、比率给分母等）变成必答，违反即判错。当时承诺「归为指令遵循，与 SQL 写错分开统计」，但主数字从未拆开，所有判错都混在「准确率」里。
2. 用户审 T31 判定单时发现，大量判错只是交付形式不同，数值本身对。L1plus 残余归因里，两家独立把 82 次判错中的 44 / 39 次标为「只是呈现不同」（`reports/results/l1plus-error-attribution.md`）。v3 的三条保守规则只找回其中一小部分。
3. 调优补丁 `semantic/tuning/SQL-L1.instructions.yaml` 里，O2–O7 与 8 条 Sx-out 主要是交付格式；SQL-L1-tuned-instr、SQL-L1plus-tuned-instr 的增益因此混有「学会参考答案的格式」，SQL-L1-tuned 的示例 SQL 也可能间接起作用。不拆开，就说不清调优和叠加到底提高了多少理解。

## 二、裁决

1. **两个数并列报告，所有单元同样处理：**
   - **准确率**：查询结果在内容上回答对了问题即算对，交付形式不论。
   - **按约定交付率**：内容正确，并且符合系统提示第 6–15 条与题目要求的交付形式。现行 v2 判定就是这个口径。
2. **「内容正确」怎么判**：先用确定性规则（T31 按用户判定单归纳的 v4 候选，用户审定后实施）；规则判不了的作答交给非 DeepSeek 的大模型终审，用户抽查。只需处理 v2 判错的作答。规则和终审都是看过错例后定的，报告写明。
3. **调优相关单元单独拆解**：SQL-L1-tuned、SQL-L1-tuned-instr、SQL-L1plus-tuned-instr 两个数都报，并报 tuned → tuned-instr、L1plus → 叠加单元的差距在两种口径下各是多少；补丁条目按「写法避坑（O1、P1–P6）」「交付格式（O2–O7、Sx-out）」「声明假设（O8）」三类在报告里列明。
4. **不重跑模型**：全部用现有日志离线重评；评分器 v2 不改，新口径另起实现。
5. **v3 中期报告**：涉及调优、叠加、单元排序的结论，等两个数出来后再定稿。

## 三、没改什么

- 系统提示、题库、参考答案、评分器 v2、已冻结的 tag 都不改；历史 run 不改写，新口径的重评写新的 run 目录。
- 体验约定照旧留在系统提示里，作为交付要求继续测。
